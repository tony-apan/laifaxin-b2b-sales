# 网站资料增强模块 SOP

> **定位**：这是 S0a 旁边的独立可选增强模块，不是 S0-S12 的新节点。没有网址、用户跳过、网页打不开或模块失败时，原流程照常继续；不得因此进入 `ERROR_BLOCKED`。

## 1. 什么时候触发

开局必填只有：**纯个人昵称 + 卖什么**。

以下全部选填：

- 卖给谁；
- 卖到哪；
- 用户自己的官网、产品页或产品目录；
- 卖点、认证、产能、最低起订量、交期等补充资料。

用户没说卖给谁/卖到哪时，AI 根据产品先提出客群与市场建议，标为 `ai_analysis`，不得冒充用户输入，也不得反复追问或阻断。

用户主动提供网址，或 AI 邀请一次后用户愿意提供，才触发本模块。AI 只邀请一次：

> 如果有您自己的官网、产品页或目录，可以发给我；我会读取公开页面，帮您提炼公司和产品信息。没有也可以直接继续。

## 2. 先确认网址角色

角色值域固定为：

| 角色 | 含义 | 后续处理 |
|---|---|---|
| `OWN_COMPANY_SITE` | 用户自己的公司/品牌官网 | 可提炼公司和产品候选资料 |
| `OWN_PRODUCT_PAGE` | 用户自己的产品详情页 | 可提炼当前产品候选资料 |
| `OWN_CATALOG` | 用户自己的产品目录 | 可提炼当前产品线、规格等候选资料 |
| `BUYER_SEED` | 老客户、理想买家或询盘方网站 | 转到现有 S3 种子流程，不进入用户档案 |
| `THIRD_PARTY_REFERENCE` | 竞品、平台店铺、行业文章等 | 只能辅助分析，不得成为用户公司事实 |
| `UNKNOWN` | 无法确认归属 | 只问一次用途；未确认前不得导入 |

用户原话是网址角色的首要依据，但不能绕过已知平台/社交域冲突检查。启发式分类只能提示，不能擅自把普通网址判为用户自己的资产。已知电商平台、社交媒体或第三方目录与“自己官网”声明冲突时，必须标为 `UNKNOWN + conflict`，请用户核对。平台域清单是常见域的安全提示，不是穷尽列表；未命中也不等于自动属于用户。`www.example.com` 与 `example.com` 视为同一 host；产品子域、CDN 或独立目录域名必须逐个由用户确认，不能自动放宽到整个注册域。

## 3. AI 如何访问网站

网站访问由当前 AI 的浏览器/读取能力完成；`website_profile.py` **不联网、不爬站、不绕过限制**，只接收 AI 已读取后整理的候选 JSON。

AI 默认最多读取 10 个与当前产品高度相关的公开页面，优先级：

1. 用户指定的产品页或目录；
2. 首页；
3. About / Company；
4. Products / Categories；
5. Certificates / Quality；
6. Manufacturing / Factory；
7. Contact。

边界：

- 候选和来源证据只接受 HTTPS URL。用户给 HTTP 老站时，AI 可先尝试同 host 的公开 HTTPS 地址；HTTPS 不可用就说明限制，转目录/截图/文件/文字路径，不把不安全地址写入候选；
- 不登录后台，不绕过验证码、robots、地区限制或访问控制；
- 多产品网站只提炼当前产品相关内容，其他产品仅作“相关产品线”；
- 网站打不开时说明真实原因，可降级为目录、截图、文件、粘贴文字或一句话产品；
- 不要求用户重复提供网站已经写明的信息；
- Contact 页只允许识别用户自己公司的公开业务邮箱，不收集第三方客户联系方式。

## 4. 候选资料必须分六区

运行时候选文件位于项目目录，不进入正式档案：

`runs/<operator_key>/<product_key>/website-profile/website-profile-candidate.json`

六区不得混用：

| 分区 | 含义 | 能否进入正式档案 |
|---|---|---|
| `facts` | 有页面原文和来源 URL 的可核实信息 | 用户批准后可以 |
| `company_claims` | 官网自称，如“行业领先”“全球供应” | 用户批准后可作为企业自述；不得改写成客观事实 |
| `ai_analysis` | AI 推演的客群、市场、定位或周期 | 不能作为网站事实；用户确认后另走现有产品档案流程 |
| `recommendations` | 定位、卖点表达、网站补充项等优化建议 | 不能自动导入事实，也不能直接修改线上网站 |
| `conflicts` | 页面之间或网站与用户说法冲突 | 未解决前整份相关补丁拒绝导入 |
| `unverified` | 缺原文、缺来源或仍需核实 | 不得导入 |

每条候选至少包含：`id/text/source_url/evidence_text/confidence/confirmation_status/target_profile/target_field`。

硬事实包括数字、认证、产能、最低起订量、交期、价格、年份、面积、员工数等。硬事实必须有具体 HTTPS 来源 URL 和可对照的页面原文；没有就放 `unverified`，禁止用行业常识补写。

## 5. 生成、批准和导入

标准顺序：

1. AI 访问公开页面并生成候选 JSON；
2. `validate-candidate` 校验六区、网址角色、来源 host、证据和第三方资料；
3. AI 按 `output-templates/S0a-网站资料确认.md` 展示事实、冲突、AI 分析和优化建议；
4. 用户明确选择哪些候选事实写入公司档案或产品档案；
5. `prepare-patch` 分别生成 company/product 补丁；**一次补丁只能改一个正式档案**；AI 必须把选中条目 ID、目标字段、修改前后和 `patch_id/patch_sha256` 展示给用户；
6. 用户明确批准本次展示后，运行 `approve-patch --patch <补丁路径> --ack-patch <patch_id> --by <纯昵称> --quote '<用户原话>'`；工具校验 ack 与当前补丁一致并把批准信息纳入 canonical hash；
7. `apply-patch --patch <补丁路径> --profile <标准档案路径> --project <operator_key/product_key>` 重算批准补丁 canonical hash、正式档案 base hash、项目键与标准路径，通过后对正式档案单文件原子写入。

公司补丁允许字段：`company_name/website/contact_email/target_markets/default_languages`。禁止修改 `operator_key/nickname`。由于 operator-profile 跨产品共享，v1 只允许在该运营方尚无任何 `operation-record.md` 的 S0/S0a 建档阶段自动导入，且必须**先导入公司补丁、再初始化产品档案**；已有项目后改公司资料，改走现有 `operator_profile.py update`，并由 AI 逐项目评估影响，禁止拿单项目补丁静默影响其他产品。

产品补丁只允许修改 ①到⑧固定字段及其 `source/confidence`。导入后产品档案回到 `draft`、版本递增、旧确认清空；必须按现有 `product_profile.py confirm` 再向用户确认后，才能进入 S2 或被下游使用。

## 6. 原子性、冲突与失效

- 补丁绑定 `project + target + base_profile_sha256 + patch_sha256`；批准后的 `canonical_patch_sha256` 覆盖补丁内容与批准信息，apply 时重算核验。`candidate_sha256` 只保留候选血缘供审计，apply 不重新读取候选原件；审批后不联网重新抓取。
- base hash 变化、项目不符、补丁被改、角色不允许、存在冲突/未核实字段时，整份补丁拒绝；不做部分导入。
- 项目锁和锁清理 guard 都记录 PID/项目：活进程持有时拒绝并发；明确死 PID 自动回收。损坏或零字节锁在 5 分钟内失败关闭，超过 5 分钟且文件在核验期间未变化才按陈旧锁清理，避免崩溃后永久卡死或误删后来者锁。
- 正式档案使用同目录临时文件原子替换；档案写入失败时字节与修改时间不变。批准补丁归档和影响清单是可核验的派生记录：若进程在正式档案提交前被强制终止，下次 apply 仅在 profile 仍等于 base hash、现存 sidecar 与当前批准补丁逐项吻合时自动清理并重试；内容不符则失败关闭、保留证据。
- `S12` 已激活项目拒绝导入产品补丁：`apply-patch` 会自动发现同目录 `operation-record.md`，调用者不能靠省略 `--record` 绕过；必须先用现有停用流程停止线上发送，再更新档案。
- 成功导入只生成 `website-profile/approved/<patch_id>-impact.json`，记录受影响字段和建议最早复核节点；**模块不修改 operation-record、不推进或阻断主状态机**。
- 正式 product-profile 再次确认后，由现有档案/下游 hash 机制决定旧客群、审计、模板或序列是否失效。

建议影响范围：

| 变化 | 建议最早复核 |
|---|---|
| 产品定位、产品线、目标客群或市场 | S2 |
| 核心卖点、客户线、合规边界 | S4 |
| 规格、认证、差异化、可引用数字 | S7 |
| 语言、采购周期或跟进节奏 | S9 |

仅抓取时间、检查时间等元数据变化不触发业务复核。

## 7. 模块失败与退出边界

退出码：`0=成功 / 1=文件或内部错误 / 2=输入校验失败 / 3=目标已存在 / 4=未批准或哈希不符 / 5=跳过或无变化 / 6=冲突 / 7=网址角色不允许`。

任何非 0 只表示网站增强未完成：

- 不修改正式档案；
- 不修改 operation-record；
- 不影响没有网站资料的原流程；
- AI 用人话说明原因和可选降级路径，然后继续 S0/S0a。

## 8. 用户确认时怎么展示

必须分四块展示：

1. **网站中有原文依据的资料**：结果 + 来源页面；
2. **需要用户核对的冲突/硬事实**：只列影响客群或邮件的关键项；
3. **AI 分析**：推荐客群、市场、产品定位，明确不是网站事实；
4. **优化建议**：卖点表达、网站缺口和后续建议，明确不会自动修改线上网站。

用户可回复：

- `确认导入公司资料：<条目ID>`；
- `确认导入产品资料：<条目ID>`；
- `只保存事实`；
- `修改：...`；
- `跳过网站增强`。

“确认”必须绑定本次展示的条目 ID 和补丁哈希；不能拿以前的泛化确认授权新补丁。

## 9. 兼容性硬标准

- 网站模块目录删除后，S0-S12 原流程仍能运行；
- 旧项目不迁移、不自动生成空候选文件；
- 未提供卖给谁/卖到哪/官网时，不阻断、不重复追问、不伪装成用户输入；
- 模块不需要 token/orgId，不调用来发信 API；
- 候选文件不参与现有 product-profile hash；只有批准并导入正式档案后才改变正式 hash；
- 不自动修改线上官网、线上模板、联系人、序列或激活状态；
- 买家网址只走 S3，第三方参考只做分析，均不得写成用户公司事实。
