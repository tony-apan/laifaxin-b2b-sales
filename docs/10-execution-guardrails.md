# 10 · 执行护栏（模板必读 + 越权禁止）

## 一、为什么 AI 没读模板（根因，不是态度问题）

| # | 根因 | 证据（2026-10-21 实跑） |
|---|---|---|
| R1 | 模板只在 SKILL 里"提到"，没有**进入执行路径**：AI 生成回复时没有任何一步依赖模板文件 | 我自画了 S2/S3/S5 的表格，25 个模板一个没打开 |
| R2 | 没有**失败会疼**的校验：不读模板也能把流程跑完（保存也成功了） | 6200 家保存成功，全程没触发任何模板检查 |
| R3 | 上下文太长（90+ 轮）后，AI 靠"记忆里的格式"输出，记忆被自身前几轮的自创格式污染 | 第二轮我沿用第一轮自创表头，而不是 S6 模板 |
| R4 | 模板散在 output-templates/，没有"当前节点该用哪个"的映射表 | 我要靠 grep 才找到 docs/04-tags-views |
| R5 | 规则本身冲突（标签带不带语言），AI 遇到冲突时倾向"自己发明一个" | 我建了纯中文标签，与黄金公式不符 |

## 二、三个机械化护栏（不依赖 AI 自觉）

### G1 节点门禁：node_gate.py <节点> —— 先过闸再说话
- 输入：节点名（S0/S2/S3/S5/S6/S7/S11…）
- 输出：①该节点唯一该用的模板路径 ②该模板必填字段清单 ③本次节点专属硬约束（如 S5 的 2 万点上限）
- 行为：字段缺失时**退出码非 0**；AI 必须先跑 gate 并按其清单填，才能进下一步。
- 与现有 `tools/gate_check.sh` 合并（那个已在跑连接检查，扩展成节点级）。

### G2 渲染留痕：写操作前必须落一个 render 文件
- 路径：`.local/renders/<节点>-<taskid>.md`（gitignore）
- 保存类工具（refine/company-save 封装）在执行前检查：
  1. 该 render 文件存在；
  2. 含模板必填字段（正则断言，如 `标签.*id=`、`折合.*点/邮箱`、`单次上限`）；
  3. 含**用户授权原句**：`AUTH: <用户原话>`；
- 任一不满足 → **拒绝调用平台 API**（不是警告，是硬失败）。
这就是把"AI 要老实"变成"不老实时代码跑不通"。

### G3 授权令牌：AUTH 行 = 越权的机械阻断
- 任何写操作（保存/发信/建模板/建序列/激活）都必须带 `AUTH: "<用户对该动作的原话>"`。
- 校验规则：原话里必须出现该动作的关键词（如"保存"/"发信"）+ 数量或对象。
- 反例（本次）：用户说"标签按照 A" → 原话不含"保存/扩量"，因此**扩量必须被拒绝**。
- 授权一次只能用一次（写入 operation-record 后失效）。

## 七、契约审查后的定位修订（2026-10-21，重要）

两席独立审查一致指出：P0 原方案把"本地文件标记"当安全边界是**错的**。已在任务书加「P0 修订 v2」。

### 审查给出的三条 🔴（均成立）
1. **render 可伪造/重放**：自己写文件、乱码蒙正则、复制别的 task、重放旧文件都能过。
2. **AUTH 不能证明是用户授权**：`check(action, quote)` 收到的是调用方传的字符串，写"保存 100 家"即可授权；"不要保存100家"也含动作词。
3. **一次性标记非原子**：先查后写，两进程可双花。

### 我们的战略结论（必须诚实写在这里）
- **同一进程内，AI 既可写代码又可写标记文件，因此任何本地机制都无法证明"这是用户授权的"。**
- 所以护栏的定位只能是：**让"跳步/超范围/复用票据"在代码层面跑不通**，而不是"防恶意"。
- 真正的硬边界只有两条：
  ① **收口**：唯一写入口 save_company()，其他路径不存在；
  ② **零副作用**：拒绝路径必须 http_calls == 0（用 mock 计数器断言，不是看退出码）。
- 因此 v2 修订：render 改结构化 JSON + params_hash + 30min 新鲜度；auth 改 ticket+payload_hash+O_EXCL 原子消费；测试新增 6 项反例（含并发双花、"不要保存100家"）。
- **不做的**：不做签名/秘钥（本机可改代码，做了是假安全感）；不承诺防恶意。

## 八、V3-7 汇报留痕与现役写授权（2026-10-21 落地）

1. **旧脚本禁用（部分已加物理封条）**：8 个旧写脚本 + 5 个删库脚本列入禁用清单；其中本仓现存 4 个（save_first_n/contact_add/delete_all_products/wait_save_done）已在最早可执行位置调用 `save_guard.require()`（--help 仍可用、dry-run 也封），但**仍不是安全边界**（可删封条/伪造模块绕过，与 RULES 边界声明一致）；其余旧脚本只是文档层约束。
2. **现役写授权（按实际分层）**：S5 保存=`save_company_cli.py` 的 plan/confirm/execute + `save_guard` V2 ticket；S10 加人=`contact_add_authorized.py` + `auth_guard.authorize_write(action="sequence")` 票据；模板/序列/激活=`approval.py require_approval()` 审批凭证（参数哈希绑定、confirm+confirmed 才可用；S12 另加原话校验）。`authorize_write()` 当前只覆盖 S10 加人，并非模板/序列/激活。
3. **唯一保存入口**：`tools/save_company_cli.py` 注入真实 HTTP，内部仍走 `save_company()`；旧保存脚本不再可用。
4. **汇报留痕**：`save_company()` 成功返回 `report_text = render.output + "\n" + "[render:<sha12>]"`，必须原样发给用户。`verify_report` 校验 30 分钟新鲜度（ts+mtime）、task_id 派生、正文与 render.output 一致；缺后缀/改数字/过期一律拒。
5. **count 绑定**：`render.count` 必须等于 payload 派生的 count；`save_company()` 不再接受调用方另传 count，防止同一 payload 换 count 伪造新 task_id 重复保存。同一 action+payload 成功一次后落 payload 级 ok 标记，二次保存直接 E_AUTH_REUSED。
